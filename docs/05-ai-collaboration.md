# 05 · AI 协作与验证

## 1. 目标

题目明确要求 `report.md` 写清：

- README 没写到的地方是怎么决定的。
- 怎么确认 AI 写的代码是对的。
- 用到了哪些 rules 和 skills。
- 还有哪些地方没做完或不放心。

这份文档就是日常记录，最后汇总成 `report.md`。**不要最后凭记忆补**，每次重要改动当天记一行。

## 2. Rules 与 Skills

### 2.1 Rules

项目根目录的 `AGENTS.md` 是硬约束，核心包括：

- 时间一律整数毫秒，区间 `[start, end)`。
- 重叠判定 `start < prev_end`，首尾相接允许。
- 只统计 `SUBMITTED`，按 `submitted_at` 的 `Asia/Shanghai` 归日。
- 总时长服务端计算，不信任客户端。
- 所有查询带 session 里的 `tenant_id`。
- 视频流必须鉴权 + Range。
- 提交后锁定。
- 空提交必须 `confirm_empty=true`。

使用方式：

- 每次让 AI 改代码前，先让它读 `AGENTS.md` 和相关文档。
- 每次改完，让 AI 自查“这次改动违反了哪些硬约束”，再人工复核。
- 如果 AI 的建议与 `AGENTS.md` 冲突，以 `AGENTS.md` 为准；要改规则先改文档。

### 2.2 Skills

计划在开发中使用的可复用检查流程（如果工具支持，就落成项目 skills；否则用固定 prompt 执行）：

| Skill | 用途 | 触发时机 |
|---|---|---|
| `domain-review` | 检查区间、时长、时区、提交口径 | 每次改 `domain/`、`services/` |
| `api-contract` | 检查 API 契约、错误码、权限矩阵 | 每次新增/修改接口 |
| `tenant-isolation-review` | 检查所有查询和视频流是否带租户 | 每个后端 PR/改动 |
| `ux-review` | 检查 loading/empty/error/unsaved、键盘、可访问性 | 每个前端页面完成时 |
| `release-check` | 跑全量测试、启动、Range、seed、README | 每个里程碑结束 |

在 `report.md` 里只写**实际用过**的；没用上的不要列。

## 3. AI 工作流

每次改动按这个顺序：

1. **写清楚要改什么**：功能、涉及文件、必须遵守的规则。
2. **先写失败测试或验收用例**：尤其是区间、时区、租户、并发。
3. **让 AI 实现**：提供上下文和约束，不接受“顺手重构”扩大范围。
4. **看 diff**：逐行检查，不只看测试是否通过。
5. **跑测试**：记录命令和结果。
6. **手工验证**：浏览器、curl、数据库至少选一个。
7. **记录**：在本文第 6 节追加一行。
8. **更新文档**：API/决策变更同步。

### 3.1 适合交给 AI 的

- 脚手架、依赖配置、Dockerfile、Nginx 配置初稿。
- CRUD 路由和 Pydantic schema 初稿。
- React 页面和组件的初稿。
- 测试用例生成（但必须人工审边界）。
- 文档初稿、API 表格整理。
- 重复性重构、命名、格式化。

### 3.2 不适合完全交给 AI 的

- 领域规则（重叠、时长、时区、提交口径）的最终实现和审查。
- 租户隔离和权限判断。
- 视频流 Range/鉴权/大文件处理。
- 并发领取/提交的事务边界。
- 最终手工验收和 report 的诚实性。

AI 可以写第一版，但这些地方必须逐行看懂、自己改、自己测。

## 4. 常见 AI 失败模式

| 失败模式 | 后果 | 检查方式 |
|---|---|---|
| 用 `start <= prev_end` 判重叠 | 首尾相接被误判 | 单测“相邻允许” |
| 用 `created_at` 统计 | 归日错误 | 检查 SQL + 时区测试 |
| 用 UTC 日期归集 | 晚间提交跑到第二天 | 23:59 / 00:01 测试 |
| 从请求体取 `tenant_id` | 越权 | 跨租户 API 测试 |
| 只在前端过滤租户 | 直接调 API 穿透 | 后端每个查询检查 |
| 信任客户端 `duration_ms` | 片段超出视频 | 服务端 ffprobe + 边界校验 |
| 用浮点秒累加 | 精度漂移 | 全链路整数毫秒 |
| `read()` 整个视频 | 500 MB 内存爆 | 流式上传 + Range 分块 |
| 视频流不鉴权 | 跨租户泄露 | 未授权 404 测试 |
| Range 返回 200 全文件 | 拖动卡死 | curl 206 验收 |
| 领取“先查再插”不加锁 | 两人同时领取 | 并发测试 + 部分唯一索引 |
| 重复提交不拦 | 统计重复 | 409 测试 |
| 草稿计入统计 | 数字虚高 | 统计测试 |
| 零长度片段 | 脏数据 | `end > start` 校验 |
| SQL 字符串拼接 | 注入 | ORM/参数化检查 |
| 缺少 loading/error/empty | UX 差 | 页面状态清单 |
| 复制通用 CRUD UI | 视觉分低 | 工作台专门设计 |

## 5. 验证证据清单

## 7. report.md 提纲

最终 `report.md` 建议结构：

```markdown
# Report

## 1. 我如何理解题目
- 业务背景与目标
- 角色与主流程
- 四条硬规则

## 2. 关键决策
- 表格：问题 / 选择 / 备选 / 理由

- 角色与权限矩阵
```

## 8. 可直接使用的检查 Prompt

```text
读 AGENTS.md 和 docs/01-decisions.md。检查这次 diff 是否违反以下约束：

3) 统计是否用 submitted_at + Asia/Shanghai；
```

## 9. 未完成/不放心模板

最后按这个格式写，越具体越好：

```markdown
### 未完成
- 任务提交后的退回/重开：本期决定锁定，未实现。
- URL 导入视频：未实现，只支持本地上传。
- 移动端专门适配：只保证不崩，未做触控优化。
- 按标注员统计/CSV 导出：可选，未实现。

### 不放心
- Safari + AV1：只在 Chrome 验证过；Safari 可能黑屏，README 已注明推荐 Chrome/Edge。
- 500 MB 上传耗时：本地验证通过，但评审网络环境未知。
- 并发领取：单机 PostgreSQL 测试通过，未做多实例压测。
- 时区：固定 Asia/Shanghai；如果部署到其他时区需改配置。
```

## 10. 诚实原则

- 不写“全部完成”如果有关键项没做。
- 不写“测试充分”如果没有具体用例和命令。
- 不把 AI 生成的代码说成自己逐行写的；说清楚哪些是 AI 初稿、哪些自己改了。
- 不隐藏已知限制；评审更愿意看到“知道问题在哪”，而不是“假装没问题”。
